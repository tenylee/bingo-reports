📋 项目背景

千广传媒日常工作繁忙，需要在飞书里说"创建任务"时，任务直接写入嘀嗒清单（TickTick），而不是 Apple Reminders。

❌ 失败的4次尝试
尝试 1：禁用 apple-reminders 技能
在 OpenClaw gateway config 里将 apple-reminders 设为 enabled: false，期望 AI 转而选择 ticktick-applescript
失败 · apple-reminders 是内置绑定技能，不受 user-level config 控制
尝试 2：提升 ticktick-applescript 优先级
设置 order:1 最高优先级，加载到 skills.entries，设为默认技能
失败 · 模型仍然选择 apple-reminders
尝试 3：强化 ticktick-applescript SKILL.md 规则
在技能文件里加入大量禁止规则和触发词，说明禁止使用 remindctl
失败 · 模型完全忽略技能文件里的规则
尝试 4：AGENTS.md 工作区硬规则
在工作区规则里写明"创建任务必须用 osascript + TickTick"
失败 · 模型知道规则存在但仍然选择 apple-reminders
🔍 核心问题分析
💡 为什么会失败？

问题的根源不在于"如何让 AI 选择 TickTick"，而在于"无论怎么配置，AI 都会优先选择它默认的 apple-reminders 技能"。

无论怎么调整优先级、加规则、禁配置，OpenClaw 的模型都会坚持调用 remindctl add，因为这是它训练时学到的默认行为模式。

换一个思路：与其改变 AI 的选择，不如在 AI 选完之后，拦截它的执行。

✅ 最终方案：命令拦截
飞书AI说"创建任务"
→
调用 remindctl add
→
被 ~/.zshenv 拦截
→
转发给 TickTick
🔑 关键技术：在 ~/.zshenv 里定义 remindctl 函数

当 AI 调用 remindctl add "任务标题" 时，拦截器自动把它转成 AppleScript 命令，写入 TickTick。整个过程对 AI 透明——它完全不知道底层已经替换。

# ~/.zshenv — 命令拦截器核心 remindctl() { local REAL="/opt/homebrew/bin/remindctl" local TITLE="" local TDUE="" if [[ "$1" == "add" ]]; then # 解析标题和时间参数 TITLE="$2" # ... 参数解析逻辑 ... # 转发给 TickTick osascript -e "tell application \"TickTick\" to add task given title:\"$TITLE\", due date:\"$TDUE\", priority:3" echo "✓ $TITLE [嘀嗒清单] — 已创建" else # 非 add 命令走真正的 remindctl $REAL "$@" fi }
🧠 为什么这个方案能成功？
不改变 AI 的行为，而是改变行为的结果。

AI 仍然调用它熟悉的 remindctl add，我们不阻止它，也不告诉它为什么——我们只是在 shell 层面悄悄改写执行。

这种"透明拦截"的思路绕过了所有 AI 层面的配置难题，因为拦截发生在 AI 决策之后、执行之前。
